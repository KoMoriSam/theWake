## They're both paginators; I wasn't trying to show anyone up!

### `splitMarkdown`: ~~Paginator~~ Slicer 1.0

The old reader called `splitMarkdown` to divide a chapter into chunks, then treated each chunk as a page. It knew nothing about the reader's screen height, font size, line height or paragraph spacing. Change the phone's dimensions or increase the font size by a couple of steps, and the same Markdown still produced exactly the same chunks.

A “page” was therefore just an array element. It might fill the screen, or contain only a short paragraph. Readers had to scroll to the bottom before finding the previous/next page or chapter buttons. Continuing along that path would have meant estimating paragraph heights before rendering Markdown. Images, blockquotes, lists, code blocks and footnotes would only make those estimates drift further.

The better approach was to paginate after Markdown had become DOM. The browser handles line wrapping; the code works out the size of each column and which column to show. Page numbers now change with screen dimensions and typography settings, so paragraph IDs containing page numbers (`{uuid}-{page}-{paragraphIndex}`) no longer suit the new mechanism. `{uuid}-{paragraphIndex}` is enough.

### CSS columns: Paginator 2.0

> [!note]
> CSS columns are hardly new; people shared implementations like this long ago. Why didn't I use them? Partly because I was lazy, and partly because AI wasn't as capable back then. The pagination ~~we built together~~ was painful to look at.

Back to the point. Browsers already provide a layout system close to pagination: CSS Multi-column Layout. Give an article a fixed width and height, then make the column width equal the page width. Text flows from the first column into the second, then the third:

```css
.mobile-page-article {
  height: var(--reader-page-height);
  width: var(--reader-page-width);

  column-width: var(--reader-page-width);
  column-gap: var(--reader-page-gap);
  column-fill: auto;

  overflow: visible;
}
```

The reader viewport hides the other columns. Changing pages does not require rendering Markdown again; the entire article simply moves to the left:

```css
.mobile-page-article {
  transform: translate3d(
    calc(var(--reader-chapter-offset, 0px) - var(--reader-page-offset)),
    0,
    0
  );

  transition: transform 220ms cubic-bezier(0.2, 0.8, 0.2, 1);
}
```

Here:

```js
const pageStride = pageWidth + pageGap;
const pageOffset = (currentPage - 1) * pageStride;
```

Every page still belongs to the same DOM tree. Paragraph IDs, paragraph comment buttons, footnote references and search anchors do not need to be duplicated for pagination.

Counting pages did expose a pitfall. In some mobile browsers, `scrollWidth` for a multi-column layout only includes the first column. Dividing it by the page width can make an entire chapter look like a single page.

The paginator now locates the final character of the body, gets its position with `Range.getClientRects()`, and calculates the final page number:

```js
const lastTextPage =
  Math.floor(Math.max(0, lastTextLogicalLeft) / pageStride) + 1;

if (lastTextRect) return Math.max(1, lastTextPage);
```

An end marker is only used as a fallback when the body has no measurable text. This also avoids creating an empty final page when the marker alone spills into a new column.

#### How tall is a page?

Can the page height just be `100vh`? If nothing else interferes and all you want is fullscreen reading, certainly. But this site has a bottom dock, and the browser has a `visualViewport`. A mobile address bar expanding or collapsing, an orientation change, or an on-screen keyboard can all alter the visible area.

The current implementation therefore reads:

- The top of the reading viewport;
- The bottom of `visualViewport`;
- The top of the dock;
- The gap reserved between the reader and the dock.

It then calculates the height actually available for the text:

```js
const availableHeight = Math.floor(
  Math.min(dockTop, visualBottom) -
    viewportTop -
    PAGE_DOCK_GAP,
);
```

Knowing the height is not enough to start pagination immediately. Using the user's preferred line height directly usually leaves a small strip of space at the bottom. The first lines on different pages align, while the final lines can end at different heights.

The paginator first calculates how many complete lines fit:

```js
const lineCount = Math.max(
  1,
  Math.floor(contentHeight / preferredLineHeight),
);
```

It then adjusts the line height to fill the body area exactly:

```js
const pageLineHeight = contentHeight / lineCount;
```

The adjustment is usually small, but the first and last lines of each page now share the same top and bottom baselines.

For technical reasons, the reader currently cannot support arbitrary paragraph spacing. For now, I quantize it to multiples of half a line height:

```js
const paragraphGap =
  paragraphGapHalfSteps * (pageLineHeight / 2);
```

> [!note]
> In fact, the current layout system is unfinished. Only spacing in whole multiples of the line height can currently align both the first and last lines.

If footnotes, blockquotes or other block elements leave less than a line of unused space at the bottom, the paginator gathers the existing gaps between blocks and distributes the missing height across them. It then checks the page count and footnote assignments again. If either changes, it rolls back that correction.

The chapter header is treated as a single block. The reader measures the entire `ChapterHeader`, then pads “header plus gap before the body” to a multiple of the line height. The title, word count and update time still use the desktop component; aligning each separately would pull the header apart.

#### Endnotes or footnotes?

On desktop, notes can all sit at the end of an article. On mobile, with horizontal pagination, leaving notes at the end of the chapter means readers may have to turn through many pages after seeing a reference marker.

The mobile reader therefore hides the endnote section generated by Markdown, scans `.footnote-ref` elements in the body, and assigns notes to the pages containing their reference markers. Pages without notes reserve no space. For pages with notes, it renders the same `PageFootnotes` component off screen to measure its actual height:

```js
measuringFootnotes.value = notes;

await nextTick();
await waitForLayout();

const measuredHeight = footnoteMeasureRef.value?.scrollHeight || 0;
```

The footnote area reuses the desktop separator, numbering and text styles, with smaller mobile margins. It reserves the measured height while ensuring that at least three body lines still fit on the page.

That creates another problem: the browser has already filled the page with text. When footnotes suddenly occupy the bottom, the final lines overlap them. Moving the entire paragraph to the next page can leave a large blank area. Instead, the current implementation searches for the first character extending below the top of the footnote area:

```js
const hasOverflowingRect = Array.from(
  range.getClientRects(),
).some((rect) => rect.bottom > footerTop);
```

Once it finds the split point, the paginator extracts the remaining text as a continuation paragraph and forces it into the next column:

```css
.mobile-footnote-continuation {
  margin-block-start: 0;
  break-before: column;
}
```

Splitting the DOM makes the browser think the first part of the paragraph has ended. Its final line must therefore remain justified:

```css
.mobile-footnote-split-source {
  text-align-last: justify;
}
```

If the split falls exactly at the start of a paragraph, the entire paragraph moves to the next page and keeps its two-character first-line indent. A genuine continuation loses the indent.

After laying out footnotes, the reader counts pages again, because forced column breaks push later content forward. The process can run for several rounds, until every page has room for its footnotes or the layout iteration limit is reached.

#### About those blank-page bugs

Font size, line height, paragraph spacing, screen dimensions and font loading can all trigger pagination again. A single pagination run itself has several asynchronous stages:

1. Wait for Vue to update the DOM;
2. Wait for browser layout;
3. Measure the page count;
4. Collect footnotes;
5. Measure their height;
6. Insert column breaks;
7. Correct page baselines;
8. Restore the reading position.

If the user changes the font size again halfway through, the old task may keep modifying the new DOM using the previous line height. The result mixes two sets of measurements, and a blank first page appears.

Each measurement now gets a token. A new layout request immediately invalidates the previous token:

```js
const token = ++measureToken;

if (token !== measureToken) return;
```

While a task is running, the next request is queued and only runs after the current one exits. Paragraph splits for footnotes, forced column breaks and baseline compensation from the old task are all rolled back together.

Before committing the measurements, the paginator also checks whether the first and current pages contain visible body text. If it detects a blank page, it clears the temporary layout and measures again. Only after repeated failures does it fall back to the valid page nearest the current one.

> [!note]
> Even with this, unstable layouts can still produce blank first or last pages. This bug remains unresolved.

A mobile keyboard also changes `visualViewport.height`. Pagination freezes while the page-number input or book search has focus. It resumes after the input loses focus and the viewport settles. This freeze only handles inputs within the webpage.

> [!note]
> A webpage has no reliable event telling it that the browser address bar has focus. Treating every viewport change as keyboard activity would also break normal adaptation to screen size. Consequently, opening the keyboard **outside the webpage**, or performing other operations that change the viewport, will not freeze pagination.
>
> There may be a better way to stabilize pagination, but neither AI nor I have thought of one yet.

#### Turning pages and handling taps

If the left and right tap areas are too large, tapping a paragraph comment button can also turn the page. Only the outer 18% on each side now responds to tap-to-turn. The center is left for text selection, links and paragraph comments. A horizontal swipe of more than 44 pixels can also move to the previous or next page. These elements are excluded from page-turn gestures:

```text
a
button
input
select
textarea
summary
contenteditable
data-paragraph-id
```

Paragraph comment buttons also have a 24-pixel protective margin. The reader will not intercept taps landing near them.

> [!note]
> In actual use, swiping left or right can be unreliable. For this version, I recommend the dock buttons or taps on the left and right edges.

At a chapter boundary, the page-turn action first saves a snapshot of the current page. Once the new chapter has loaded and pagination is complete, the old snapshot and new page slide in the original direction. Moving from a chapter's last page to the next chapter's first page still slides left; returning from its first page to the previous chapter's last page slides right. This makes chapter transitions seamless.

Because chapters still need to load, a slightly blurred overlay covers the reader during loading, and page turns and controls are paused to prevent repeated operations before the data is ready.

#### The bottom dock

The mobile dock offers:

- Help;
- Previous page or chapter;
- Current page and whole-book progress;
- Next page or chapter;
- Comments.

Tapping the page count in the middle opens a shared reading-controls modal. It contains the switch between horizontal pagination and vertical scrolling, book search, page jumps, return to cover, chapter list, typography settings and refresh.

Vertical scrolling uses the normal Markdown article flow. The scroll container's top and bottom boundaries also avoid the dock. Switching modes restores approximately the same position using paragraph anchors.

Swiping down from the top of the page reveals the navigation bar; swiping up within it hides it manually. Opening the navigation menu pauses the auto-hide timer, so the bar does not disappear halfway through choosing an item.

## In a sentence: usable, but still plenty of bugs

### Pagination depends on your luck

CSS columns save us from writing a line-breaking algorithm, but browsers can differ in how they handle columns, complex blocks and font loading. The current implementation works around incomplete `scrollWidth` results in some browsers; more devices still need testing.

### It only handles simple text flows

The current layout mainly targets body paragraphs, reference markers and ordinary endnotes. Very tall tables, code blocks, images and deeply nested blockquotes still rely on the browser's own column-breaking decisions.

> [!note]
> It is already sufficient for plain-text novels. For me, of course, that is not enough.

### The pagination component is too long to keep the spaghetti under control

`Mobile/PagedReader.vue` has passed two thousand lines. It handles dimension measurements, footnote splitting, gestures, the keyboard, chapter transitions, reading positions and blank-page recovery. Measurement scheduling, footnote layout and gesture handling should eventually become separate composables. Otherwise, the next pagination fix may first require me to write a reader for the reader's code.
